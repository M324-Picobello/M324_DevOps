# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

This is a school project for developing the backend for a ticketing system, with the main goal of teaching the users DevOps skills. Further documentation can be found [here](.claude\Projekt4_Ticketsystem.md)

## Behavioral Guidelines

Guardrails to reduce common LLM coding mistakes. **Tradeoff:** these bias toward caution over speed — for trivial tasks, use judgment.

### 1. Think Before Coding

**Don't assume. Don't hide confusion. Surface tradeoffs.**

Before implementing:
- State assumptions explicitly. If uncertain, ask.
- If multiple interpretations exist, present them — don't pick silently.
- If a simpler approach exists, say so. Push back when warranted.
- If something is unclear, stop. Name what's confusing. Ask.
- Project-specific: Decisions are to be explicitly made by the user. You may propose solutions to a solve prompt, which the user must decide upon.
- Project-specific: This is a school project with specific AI restrictions, which you can find documented in german [here](.Claude/KI-Nutzungsrahmen_M324.md) and [here](.Claude/Promptbibliothek_M324.md).


### 2. Simplicity First

**Minimum code that solves the problem. Nothing speculative.**

- No features beyond what was asked.
- No abstractions for single-use code.
- No "flexibility" or "configurability" that wasn't requested.
- No error handling for impossible scenarios.
- If you write 200 lines and it could be 50, rewrite it.

Ask: "Would a senior engineer say this is overcomplicated?" If yes, simplify.

### 3. Surgical Changes

**Touch only what you must. Clean up only your own mess.**

When editing existing code:
- Don't "improve" adjacent code, comments, or formatting.
- Don't refactor things that aren't broken.
- Match existing style, even if you'd do it differently (Springboot conventions).
- If you notice unrelated dead code, mention it — don't delete it..

When your changes create orphans:
- Remove imports / variables / methods / routes that *your* changes made unused.
- Don't remove pre-existing dead code unless asked.

The test: every changed line should trace directly to the user's request.

### 4. Goal-Driven Execution

**Define success criteria. Loop until verified.**

Transform tasks into verifiable goals:
- "Add validation" → write JUnit examples for invalid inputs, then make them pass.
- "Fix the bug" → write a spec that reproduces it, then make it pass.
- "Refactor X" → ensure `mvn test` (relevant files) passes before and after.

For multi-step tasks, state a brief plan:

```
1. [Step] → verify: [check, e.g. `mvn test` for running all project maven tests]
2. [Step] → verify: [check, e.g. `mvn checkstyle:check` for ]
3. [Step] → verify: [check]
```

Default verification hooks in this project: `mvn test -Dtest="TestClass"` for behavior, `mvn checkstyle:check` for style. Don't declare a task done until the relevant check passes.

Strong success criteria let you loop independently. Weak criteria ("make it work") require constant clarification.

---

**These guidelines are working if:** diffs contain fewer unnecessary changes, fewer rewrites follow overcomplication, and clarifying questions come *before* implementation rather than after mistakes.

## Branch discipline

**Never switch branches or create a new branch without explicit user confirmation.** This is non-negotiable.

- Do **not** interpret short replies like "go", "proceed", "continue" as authorisation to switch branches or create new ones. They authorise execution on the current branch only.
- If a plan or task seems to logically call for a new branch (sibling feature, separate PR), **ask first** — name the branch you'd create, explain why, and wait. The cost of a one-line confirmation is low; the cost of committing on the wrong branch is high (lost context, wrong PR target, manual recovery).
- Always check `git rev-parse --abbrev-ref HEAD` before committing and confirm with the user that this is the intended branch.
- If you find yourself on what looks like an unrelated branch (e.g. the branch name doesn't match the work), **stop** and ask — don't assume it's safe to commit anyway, and don't switch branches "to clean things up". The user may be intentionally using that branch.

## Development Commands

```bash
# Remove all files generated by the previous build. 
mvn clean

# Compile the source code of the project. 
mvn compile

# Compile, test, and package the code into a JAR/WAR file. 
mvn package

# Install the package into the local repository.
mvn install

# Deploy the package to a remote repository.
mvn deploy

# Execute a Java program.
mvn exec:java -Dexec.mainClass="org.example.Main"

# Clean the project and validate it. 
mvn clean validate

# Display the dependency tree. 
mvn dependency:tree

# Display the effective POM. 
mvn help:effective-pom
```

## Testing

```bash
# Run full suite
mvn test

# Run single class
mvn test -Dtest="TestClass"

# Run a specific test method.
mvn test -Dtest="TestClass#testMethod"

```
